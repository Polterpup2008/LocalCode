# LocalCode 1.1 — greeting overhead and GPU compatibility

## Confirmed causes

The 1.0 engine sent a greeting through the coding-agent loop. The captured
request contained 31 tool schemas, coding and verification instructions, a
selected verification skill, workspace and machine information, and repository
index guidance. There were no earlier conversation turns. On the installed 9B
model, the native template rendered **8,637 prompt tokens** for `hello how are
you`. The same model rendered **97** for the new conversational path.

The Windows distribution previously supplied a CUDA 13 runtime without a
bundled alternative. The reported older laptop driver, apparently 528.02, is
below the R580 branch required for CUDA 13 minor compatibility. That is a real
compatibility risk; the old session's actual backend/offload state remains
unconfirmed because that computer and its logs were unavailable. A zero Task
Manager 3D graph and 3.6 GB of system RAM do not establish CPU-only inference.
See [NVIDIA's driver compatibility requirements](https://docs.nvidia.com/cuda/cuda-toolkit-release-notes/index.html#cuda-toolkit-and-minimum-required-driver-version-for-cuda-minor-version-compatibility).

## Changes

The shared, Qt-independent engine now routes complete recognized social turns
to a short conversation request. Explicit Chat mode supports other conversation;
Code mode and ambiguous Auto requests retain project conventions, all permitted
tools, approvals and the verification loop. Chat executes no tool calls and does
not clear the preceding coding task's evidence. Cancellation preserves partial
text. No GPU architecture or model name is hardcoded into this routing.

The Windows package includes a matching b11829 Vulkan alternative. Runtime
selection probes actual devices, distinguishes failed enumeration from an
unfamiliar custom format, and prefers a matching dedicated adapter for bundled
Vulkan fallback. Device names are not restricted to an NVIDIA whitelist.
Offload counts come from startup logs at the runtime's supported diagnostic
verbosity. Driver updates are never performed.

New profiles use memory-aware starting recommendations, bounded saved prompt
states and automatic GPU-layer fitting with an explicit context floor equal to
the requested context. Existing context settings and explicit manual overrides
remain available. Context presets and fit/manual controls are visible in Models.
One managed slot matches the serialized agent. The tested 1.0 b11829 configuration
already reported 32K per slot with four shared slots; this is not credited as a
context-capacity increase. Model loading, prompt evaluation and generation have
separate timings.

## Real inference comparisons

Windows, i5-12450H, 32 GiB RAM, RTX 4060 Laptop 8 GiB, driver 610.78. Models were
already installed. No model download, driver update, user-app shutdown or power
setting change was performed. The CLI baseline is the previously shipped 1.0
RC5 binary. Both use the same selected b11829 runtime and exact GGUF bytes.

Each pair retains **32,768 context capacity, f16 K/V, 8 threads, 512 batch and
microbatch, temperature 0, seed 42, disabled optional reasoning and a 64-token
output budget**. These are single fresh-process observations, not a statistical
speed admission campaign. Prompt work and actual output lengths intentionally
differ. The earlier runtime's kernels are unchanged.

| Model/backend | Evaluated prompt tokens, before → after | Prompt evaluation time | Reported prompt rate, tok/s | Reported generation rate, tok/s | Time to first token |
|---|---:|---:|---:|---:|---:|
| Qwen3.5 9B Q4_K_M / CUDA | 8,637 → 97 | 5.840 s → 0.248 s | 1,478.87 → 391.09 | 32.22 → 33.50 | 5.947 s → 0.265 s |
| Qwen3.5 0.8B Q4_K_M / CPU | 8,638 → 97 | 36.978 s → 0.438 s | 233.60 → 221.64 | 23.09 → 35.78 | 37.078 s → 0.449 s |

The improvement is **98.9% less unnecessary prompt work**. Short prompts use
smaller batches and can report lower prompt tokens/second while finishing much
earlier. Generation rates here also reflect different active prefix lengths;
they do not prove a kernel improvement. Actual output counts were 61 → 31 tokens
for 9B and 64 → 19 for 0.8B.

Both before runs were deliberately limited to one agent step. The 9B model
requested a repository overview; the 0.8B model asked for acceptance criteria.
Neither completed the greeting within that limit. Both after runs gave a normal
answer in one request with no tools. Whole-process durations are retained in the
JSON, but are not presented as a matched successful-task speed comparison.
Startup was separate: 5.15 s → 5.38 s for 9B and 1.79 s → 1.77 s for 0.8B.

## Where the prompt tokens went

The actual captured requests were independently rendered through the same
pinned runtime's `/apply-template` and `/tokenize` endpoints. The totals matched
the inference reports exactly: 8,637 and 97. Removing one component at a time
from the original request produced these reductions:

| Removed component | Reduction in rendered prompt tokens |
|---|---:|
| Native tool definitions and their template expansion | 5,305 |
| Selected verification skill | 717 |
| Coding-agent instructions, identity and language guidance | 738 |
| General verification and completion instructions | 725 |
| Machine/toolchain information | 529 |
| Repository Intelligence guidance | 353 |
| Workspace context | 112 |
| Current task and verification state | 138 |

These ablations overlap at token/template boundaries and are not additive.
The human greeting itself tokenized to four tokens; older conversation history
contributed zero. Without tools, the old message framing added 15 tokens over
independently tokenized message contents. The new conversation's raw message
contents used 80 tokens and its complete formatted request used 97.

## Acceleration and constrained placement

- **CUDA, 9B:** startup reported 33/33 layers offloaded, with CUDA model, KV,
  recurrent-state and compute buffers. The context remained 32,768.
- **CPU, 0.8B:** explicit no-device selection and startup reported 0/25 layers
  offloaded. The context remained 32,768.
- **Bundled Vulkan fallback, installed 4B:** CUDA was hidden only in the owned
  child environment. LocalCode selected Vulkan1, matching the dedicated NVIDIA
  adapter instead of Vulkan0 integrated graphics, and startup reported 33/33
  layers offloaded at 32K/f16. The first use had 37.261 s first-token latency;
  a fresh-process repeat had 0.214 s, with identical settings and answer text.
  Startup was about 17 s on first use and 4.89 s on repeat. The first-use cost
  is retained; driver/pipeline cache behavior is not a LocalCode speed claim.
- **Restricted device-memory budget, 9B:** a 4,096 MiB target reserve on the real
  8 GiB GPU selected 12/33 GPU layers and retained actual 32,768 context and f16
  K/V. CPU and GPU KV buffers were 640 and 384 MiB, respectively. It answered
  normally. This exercises fitting; it does not emulate a GTX 1650 Ti.

`nvidia-smi` returned `[N/A]` for the owned process's dedicated memory counter
under WDDM. The allocation figures are startup buffer reports, not measured
live total VRAM consumption. Missing telemetry is never converted to zero.

## Coding and regression checks

The real 9B model, in Code mode, read a synthetic README and calculator sources,
changed only `calc.py` from subtraction to addition, and ran the project's
Python test command. It used six tool calls over five iterations. The untouched
test file's two arithmetic assertions passed; a separate post-run test also
passed. The application task-state verdict remained **partially verified**;
configure/build stages were not invented for this Python fixture.

Automated coverage exercises greeting/code switching, tool-call rejection in
Chat, cancellation, retained coding evidence, profile migration and manual
overrides, real child-process device probes, unknown custom formats, non-NVIDIA
device identifiers, exact context retention and offload telemetry. Full release
validation is recorded separately in `2026-10-23-low-end-validation.json`.

The [machine-readable measurements](2026-10-23-low-end.json) retain binary/model
hashes, actual output counts, failed baseline outcomes and the first-use Vulkan
result. Raw traces contain only synthetic test content and remain outside the
installer. The greeting comparison can be reproduced with
[`benchmark_agent_prompt.py`](../../tools/llama.cpp.localcode/benchmark_agent_prompt.py).

## Remaining hardware limits

The reported GTX 1650 Ti / 4 GiB VRAM / 16 GiB RAM machine still needs a direct
check with its installed GGUF and driver. Smaller model support was exercised
with the installed 4B model; the 0.8B CPU check is not a recommendation to replace
the default model. AMD/Intel GPU and Apple inference performance were not measured.
There is no claim that every model or device is faster than every other server.
See the [1.1 hardware checklist](../KNOWN_LIMITATIONS_1.1.md).
