# LocalCode runtime study — 23 October 2026

This study tests a Windows mapped-file working-set optimization and a separate
CUDA matvec experiment. It does not establish leadership over every AI server.
The scope is Windows x64 on one i5-12450H laptop, 32 GiB RAM, RTX 4060 Laptop GPU
with 8 GiB VRAM and NVIDIA driver 610.78.

## What counts as an optimization

The same GGUF bytes, 32,768-token context capacity, f16 K/V cache, 512-token
batch and microbatch, eight threads, GPU layer count, sampling settings and
output budgets are retained within each matched comparison. No context cuts,
KV quantization, model substitutions or speculative decoding are credited.
Each live run verifies the server's actual context, saves synthetic requests
and responses, and stops only processes started by the harness.

The shipped baseline is upstream b10655, commit
`cb300598d5f90189cb69d2702f4930aaf99d32a2`. The newer comparison is pinned to
[b11829](https://github.com/ggml-org/llama.cpp/releases/tag/b11829), commit
`184f6536024668e8908ab8c86033d56708e62b40`.
An upstream upgrade and a LocalCode source modification are separate changes.
The custom memory comparison changes only `llama.dll` between otherwise
identical runtime directories, using the same MSVC 14.44 Release build settings.

## Windows memory change

After all weights finish loading and repacking, the core asks Windows to remove
complete unused unlocked model-file pages from its working set. It retains
active tensor pointers, complete host-buffer spans and lazy ranges, and skips
explicitly locked mappings. File mappings stay valid and can fault pages back.
The operation follows the documented
[VirtualUnlock behavior](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualunlock).

Residency uses native `VirtualQueryEx` and `QueryWorkingSetEx` Valid/Locked bits.
It does not use psutil's Windows mapping `rss` field, which is unsuitable for
this measurement. A first diagnostic using that field was marked invalid and
replaced; it is excluded from these results.

The target is Qwen3.5-9B-Q4_K_M, 5,680,522,464 bytes. Early matched native-page
screens showed approximately 5.27 GiB versus 0.52 GiB process working set, with
5,097,455,616 versus 32,768 resident model-file bytes immediately after startup.
This is about 4.75 GiB less resident working set. It is **not** a private commit,
peak allocation, VRAM reduction or decode speed claim.

The longer admission run alternates twelve fresh server processes in ABBA order
three times. That yields six process pairs. Each process runs a warmup, a short
code prompt, a cold prompt of about 15K tokens, and a repeated cached prefix,
with 128 generated tokens per measured request. The predeclared memory gate
requires at least 20% median process working-set reduction, exact output token
and prompt-work equality, and no observed median timing regression over 5%.
Process-pair confidence intervals are descriptive for this machine and load.

The twelve-process run passed that memory gate. Median process working set was
**5.269 GiB unmodified versus 0.522 GiB modified**, a **90.092% reduction**.
All six pairs had the same mapped virtual capacity and generated token IDs.

| Workload | Median decode change | Decode paired 95% interval | Median wall-time gain | Median first-text latency gain |
|---|---:|---:|---:|---:|
| Short, 15 prompt tokens | −0.31% | −0.76% to +0.39% | −0.43% | −4.72% |
| Cold long, 15,225 prompt tokens | −0.43% | −1.10% to +0.77% | +0.07% | +0.003% |
| Cached prefix, 4 prompt tokens processed | −0.20% | −1.13% to +0.77% | −0.26% | −2.21% |

Positive means faster; negative means slower. In particular, short first-text
latency was 4.72% slower, within the predeclared 5% observed-median bound.
This does not establish latency non-inferiority on other machines or loads.
The separate 5% **speed** admission gate did not pass, and no speed gain is claimed.
The [complete paired analysis](2026-10-23-memory-analysis.json) includes every
pair and the confidence calculation's limits.

## Correctness and controls

- The 9B API/answer screen passes 15/15 for shipped b10655, official b11829,
  the rebuilt unmodified core and the modified core. It covers Unicode
  tokenization, JSON arithmetic, generated pure Python arithmetic checked
  without executing model code, native tool arguments, streaming and health.
- The modified core preserves all 255 upstream public C exports.
- Tests compile the actual patched mapping class: 20,000 interval cases,
  5,000 grouped ownership cases, nine real mapped-file views and five actually
  locked pages. Protected pages remain resident, unused complete pages are
  removed, all bytes remain exact/refaultable and locked pages remain locked.
- Dense 4B CPU, 0.8B non-mapped loading and 0.8B explicit mapping/locking controls
  produce identical 64-token outputs across four phases each. Active CPU-owned
  model pages remain resident. These controls have no claimed memory gain.
- The weaker 0.8B model passes 8/15 on both upstream versions, with the same
  per-case verdicts. Its existing answer failures are retained, not treated as
  successful model qualification.

## CUDA experiment: rejected

A CUDA-only Nsight Systems trace attributed over 85% of GPU kernel time to
quantized matvec operations. A matched SM 8.9 build then tested two output rows
per block for single-column Q4_K/Q5_K/Q6_K matvec. Arithmetic and reduction order
were retained. Correctness passed, including added odd-row Q6_K cases and other
quantization controls, with no newly unsupported cases. The live 9B screen
passed 15/15 and generated identical tokens.

The uninstrumented four-process screen measured median decode changes of
**−0.94% short, +0.07% long, +0.45% cached**. It did not demonstrate the required
5% speed gain; two process pairs are also insufficient for admission. The
experiment is rejected and its CUDA module is excluded from the release.
The stock upstream CUDA backend and complete CPU backend set are retained.

## Named server comparison: Ollama 0.40.9

The official portable [Ollama 0.40.9](https://github.com/ollama/ollama/releases/tag/v0.40.9)
build ran four fresh process trees on a private loopback port, with its own
profile/model store and cloud features disabled. The imported GGUF SHA256 was
verified, `/api/ps` confirmed 32,768 context, and logs confirmed f16 K/V, flash
attention, 512-token batch/microbatch, eight threads and all 33 layers on CUDA.
Raw generation avoids chat-template differences. No existing Ollama installation
or model store was changed.

| Server | Short decode, tokens/s | Long decode, tokens/s | Cached decode, tokens/s | Processes |
|---|---:|---:|---:|---:|
| Previously shipped b10655 (one-process screen) | 10.67 | 9.93 | 10.00 | 1 |
| Matched unmodified b11829 core | 10.56 | 9.79 | 9.75 | 6 |
| LocalCode memory core | 10.49 | 9.69 | 9.70 | 6 |
| Ollama 0.40.9 | 10.51 | 9.77 | 9.81 | 4 |

These are per-server medians from sequential runs under variable background
and thermal load, not a paired cross-provider confidence estimate. They show
similar decode rates, not a speed victory for LocalCode. Every request produced
128 tokens. All twelve Ollama responses matched native output text. Cold prompt
work was 15 or 15,225 tokens; the repeated long prefix reused 15,221 tokens and
processed four, matching the native workload. Ollama reports cached and total
prompt counts separately; those are not extra prefill work.
The one-process shipped-runtime screen also matched all output text/counts;
it is a compatibility/reference screen, not evidence of an upgrade speed gain.

The first Ollama short request had a **92.18-second** first-text delay, followed
by 0.52–0.61 seconds in the next three processes. It is retained as a first-use
outlier and is not used to assert a broad steady-state advantage. Initial model
import and warmup are outside the request table. Ollama disables mmap by default
for this Windows CUDA load, so its process memory cannot be used as the matched
reference for the LocalCode source patch. The controlled 90.092% saving above is
relative to the otherwise identical unmodified core, retaining mmap.

[Comparison statistics](2026-10-23-server-comparison.json) and
[raw synthetic Ollama rows](data/ollama-9b/results.json) retain the outlier and
the native nanosecond timing/count fields.

## Additional capacity and mixed-offload checks

A separate one-pair screen processed **31,325 prompt tokens**, then generated
128 tokens, retaining 32,768 capacity and no context shifting. Both cold and
cached output token IDs matched exactly, without truncation. Cold wall/decode
changes were within 1%. The single cached first-text measurement was 197.7 ms
unmodified versus 229.8 ms modified, a 32.1 ms increase (14% lower ratio).
This is retained as a latency concern rather than treating that one pair as a
performance pass. The focused four-process ABBA repeat used one cold prefill and five identical
128-token cached requests per fresh process. All tokens/prompt-work counts
matched. Averaging the five cached requests within each process pair gave
first-text ratios of 0.984 and 1.352 (modified slightly slower in the first pair,
faster in the reverse-order pair). It did not reproduce a consistent 32 ms
penalty. The observed median timing bounds passed in that repeat, but its two
process pairs are insufficient for a separate performance admission. No latency
or speed gain is claimed from it. The [repeat data and analysis](data/memory-near-context-repeat-9b/)
retain all twenty cached requests and the initial outlier remains above.

A **20-GPU-layer** mixed CPU/GPU one-pair screen also matched all 128 output
token IDs. Ready process working set was 5.662 versus 2.538 GiB (55.18% lower),
with 1.623 GiB of CPU-owned mapped pages retained. Observed decode change was
−0.87%. This is a compatibility/resource screen with one pair, not a second
six-pair admission or a performance claim. The corresponding
[capacity](data/memory-near-context-9b/) and
[mixed-offload](data/memory-partial-offload-9b/) rows and analyses are published.

## Limits and reproduction

User background applications were active, GPU temperature reached 86–87°C,
and software thermal throttling was observed. No user process, power setting
or GPU clock was changed. Results describe this loaded laptop; they do not
establish an idle-machine score, power efficiency, all-model compatibility or
universal speed superiority. CUDA trace timings are used for attribution only.
Linux-only servers have not been tested on this Windows environment.

The [source patch, build instructions and benchmark tools](../../tools/llama.cpp.localcode/README.md)
provide reproduction. Original llama.cpp code retains its MIT terms. New LocalCode additions use
the project's proprietary license; both notices accompany the modified core.

The published [synthetic rows, context/weight contract and native residency counts](data/memory-9b/)
contain no user conversations or filesystem paths. Replay the analysis with:

```powershell
python tools/llama.cpp.localcode/analyze_runtime.py docs/benchmarks/data/memory-9b
```

shipped core and distribution hashes to the prepared-runtime API screen,

portable payloads match; the user's installed app and settings were untouched.
